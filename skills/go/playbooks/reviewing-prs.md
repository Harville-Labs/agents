### Reviewing PRs

**You own the review, not the fix. Every finding you post was confirmed in the code and sits on the diff line it is about.**

1. **List the queue.** The forge follows the repository's remote: GitHub uses `gh`, GitLab uses `glab`. Run the review queue command in `../references/forges.md`. It lists open PRs where you are a requested reviewer and drops the ones you authored, even when you are also a reviewer on them. Skip drafts unless the user asks for them.
2. **Drop what you already reviewed.** For each PR, find the head SHA of your last review with the commands under "Your last review" in `../references/forges.md`. Skip the PR when that SHA is its current head. Tell the user the queue, with the skipped PRs and why, before you start.
3. **Review each PR in a fresh subagent.** Spawn one read-only `reviewer` subagent per PR, in parallel, on the `medium` size. Its brief gives the PR URL, your last reviewed SHA if there is one, and these steps: check the head out in its own worktree, read the PR body and the issue it closes, and read the repository's `AGENTS.md`. With no last reviewed SHA, it diffs against the PR's base branch, not `main`. With one, it diffs from that SHA to the head. If that SHA is not an ancestor of the head (`git merge-base --is-ancestor <sha> HEAD` fails after a rebase or force-push), it reviews the whole diff against the base. It returns each finding with its path, line, side (added or removed), and body, and posts nothing.
4. **Add a Recoder review.** Run the readiness check in `../references/recoder.md` once. If Recoder is not ready, skip this step and name the failed check's `fix` line in the reply. If it is ready, add these steps to each step 3 brief. They come on top of the subagent's own review and never replace it. A PR step 2 skipped gets no subagent, so no Recoder run.
   - Review only the diff from step 3, never more. With a last reviewed SHA that is an ancestor of the head, start Recoder with `--pull <url> --since <last reviewed SHA>`, per "Run a review" in `../references/recoder.md`. Otherwise start it with `--pull <url>`.
   - Before starting, look for an earlier run of that same diff with "Reuse an earlier run" in `../references/recoder.md`. If one matches, read its report and start nothing.
   - Start Recoder before reading the code, review by hand while it runs, then read its report. Add each Recoder finding inside the diff to the list, merge it with a duplicate of your own, and mark it with its `verification.status`. A Recoder `side` of `old` is a removed line, and `new` an added one.
   - Return the `runId`, the `outcome`, and any `coverageGaps` with the findings. A `failed` or `cancelled` run adds no findings.
5. **Confirm every finding yourself.** Read the code at each finding. Drop a finding you cannot confirm, a style point the formatter handles, a preference the repository's rules don't back, and one that an open thread of yours on the PR already raises. A finding names what goes wrong and the input that triggers it. A Recoder finding goes through the same check. `verified` means Recoder reproduced or traced it, so read its `verification.reason` and confirm it in the code. `unverified` is a claim to check like any other.
6. **Post one review per PR.** Put each finding in a thread on its diff line and the summary in the review body, with the commands under "Post a review" in `../references/forges.md`. A finding with no line goes in the summary. When Recoder ran, the summary names its coverage gaps, if any, and its recommended checks. Post it as a comment. Approve (`gh pr review <pr> --approve` or `glab mr approve <mr>`) or request changes only when the user said to. Never push to the author's branch.

**Reply:** each PR link in full, how many findings you posted and the most severe one, PRs you skipped and why, and your recommended verdict for each. When Recoder ran, how many of its findings you posted and dropped, the runs you reused, and any run that did not complete.
