### Bug fix

**You own this task. Plan, review, verify.** Delegate investigation and the fix to subagents, stay in the lead. Pick each subagent's reasoning effort for the job, per the Subagents section.

Be scientific. Every shipped line traces to runtime evidence. Belt-and-suspenders that "might help" is a hypothesis, not a fix. It does not ship. When evidence refutes a hypothesis, revert what it motivated. The smallest change the evidence justifies ships, nothing more.

1. Reproduce it yourself on the matching surface via the control skill (Non-negotiables), even when a debug or instrumentation protocol says to ask the user to reproduce. Get the exact symptom first: error text, input, config, version, platform. If the report is vague, read the issue, logs, and recent commits (`git log -p --since=<when it started> -- <path>`) before asking. Use the smallest input that fires it, and never the developer's real config or data (point the app's home or config directory at a temporary one, and use its mock or scripted providers when it has them). Ask the user only with a stated, specific reason the control surface cannot reach the target, and only after driving it as far as it goes. If it won't reproduce directly, synthesize the trigger, tighten conditions, or instrument until it fires. If it still won't, say what you tried. Don't fix a guess.
2. Pin it with a failing test named for the correct behavior (`keeps reasoning_details when the stream ends early`). Run it and confirm it fails for the reason in the report, not because of a typo in the test. This follows the **tdd** skill and is required whenever a local test path exists. When the only faithful repro is expensive or integration-heavy, keep the scripted repro and say why there's no unit test.
3. Binary-search the cause. Form the candidate hypotheses, then rule them out until one survives. Seed them with `how` over the affected subsystem and the **why** skill for regression history (`git blame`, `git log -S`). Each pass, take the split that cuts the most remaining problem space, get runtime evidence, eliminate. The line that throws is rarely the line that's wrong, so trace back to the first place the state went bad. When program state is unclear, add instrumentation or logging and read it as the code runs. Don't guess. Run a long or stubborn hunt under the Autonomous run playbook. Confirm the surviving *mechanism* with runtime evidence before the step-4 architect/interrogate fan-out.
4. Plan the fix. Fix the cause, not the symptom: a `try/catch`, null check, or retry that hides the bad state is not a fix unless the bad state is expected, and then a comment says why. Check whether the same mistake exists elsewhere (other providers, routes, the other client) and fix every instance or list the ones you left. If it crosses a function boundary, `architect` first. Delegate implementation to a subagent on the `medium` size (see Models in the **go** skill) with a specific scope.
5. Verify on the same surface. The original repro now passes and the pinned test is green. "Inconclusive" or wrong-surface is not a pass. Flag it. Unit tests show branch behavior, not bug absence.
6. Stage the commits so the failing test lands before the fix in git history, as `fix(<scope>): <what now works>`. This is the canonical **sequence-verifiable-units** principle skill, the failing test first and the fix on top. Note a behavior change someone could depend on in the changelog.
7. Run **Opening a PR**.

**Reply:** what was broken, root cause, fix, how you verified. Paste failing-then-passing repro output verbatim.
